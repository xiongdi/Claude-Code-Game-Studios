# 逆向文档工作流示例

## 场景

开发者构建了一个可用的技能树系统但从未写设计文档。
代码存在于 `src/gameplay/skills/`，但 `design/gdd/` 没有 skill-system.md。

---

## 会话记录

**用户：**
```
我在 src/gameplay/skills/ 中有一个可用的技能树系统，大约1200行代码。
我从未写过设计文档。我们能从实现创建一个吗？
```

**Game-Designer（读取代码，分析）：**
```
我分析了你的技能树实现。这是发现的内容：

结构：
- 3个技能树：战斗、生存、技术
- 每树5层（通过等级+先决条件解锁）
- 总计45个技能（每树15个）
- 成本：技能点（每级1点，可以花费黄金重置）

机制：
- 被动技能（属性加成）
- 主动技能（带冷却的技能）
- 协同加成（4层+跨树解锁）

实现细节：
- 数据驱动（assets/data/skills/ 中的 JSON 文件）
- 存档兼容（技能状态序列化）
- UI 显示锁定/已解锁/可用状态

在我起草设计文档之前的问题：

1. **设计意图：** 3树结构是为了代表玩家原型
   （战士/幸存者/工程师）还是玩法灵活性？

2. **重置成本：** 重置花费黄金 - 这是为了：
   - 阻止频繁重置（对build的承诺）？
   - 创造黄金下沉（经济平衡）？
   - 还是应该免费（鼓励实验）？

3. **协同系统：** 跨树协同出现在4层。这是：
   - 有意的（后期奖励混合build）？
   - 还是涌现的（意外创造了混合meta）？

4. **平衡理念：** 我看到一些技能明显更好（5层被动是+50%伤害）。这是：
   - 力量幻想（后期应该感觉超模）？
   - 还是不平衡（需要调优）？
```

**用户：**
```
好问题！这是意图：

1. 是的，3个树是原型但我想要灵活性
2. 重置应该便宜 - 我想要实验
3. 协同是有意的 - 混合build是特性
4. 是的，5层很强，但+50%可能太多了
```

**Game-Designer：**
```
完美，这澄清了愿景。让我起草设计文档：

[展示 design/gdd/skill-system.md 的草稿]

章节：
1. 概览（3树系统，混合友好，鼓励重置）
2. 设计支柱：
   - 原型清晰度（每个树有身份）
   - Build灵活性（无锁定，便宜重置）
   - 协同奖励（跨树组合可行）
3. 详细设计（树结构、解锁规则、重置）
4. 平衡框架（层功率曲线、协同限制）
5. 边缘情况（战斗中重置？最大技能数？上限？）
6. 依赖（UI、存档系统、新手教程）
7. 验收标准（所有树可行，10+混合build，清晰提示）
8. 开放问题：
   - 重置成本应该随等级增长还是固定？
   - 5层伤害加成：调优到+30%还是保持+50%？

**可以写到 design/gdd/skill-system.md 吗？**
```

**用户：**
```
是，写吧。但让我们把5层调优到+30%，并让重置成本增长。
```

**Game-Designer：**
```
✅ 已写入 design/gdd/skill-system.md
✅ 标记为 [从实现逆向文档化]
✅ 添加 TODO：在 assets/data/skills/combat-tree.json 中将5层被动更新到+30%
✅ 添加 TODO：实现增长的重置成本公式

下一步：
- 运行 /balance-check 验证技能树进展曲线？
- 创建 ADR 记录为什么是3个树而不是5个？
- 更新新手教程解释混合协同？
```

---

## 关键观察

1. **Agent 提出了澄清问题** - 不只是描述代码
2. **将意图与实现分离** - 用户纠正了"意外"不平衡
3. **设计文档捕获"为什么"** - 不只是"代码做什么"
4. **识别缺失部分** - 代码中未包含的边缘情况
5. **标记后续工作** - 平衡调优、ADR、新手教程

## 结果

设计文档现在存在，**与现实匹配**，同时捕获了**intended愿景**。未来的变更将引用此文档，新团队成员理解决策背后的*原因*。
