# Agent 测试规格：engine-programmer

## Agent 摘要
领域：渲染管线、物理集成、内存管理、资源加载和核心引擎框架。
不负责：游戏机制（gameplay-programmer）、编辑器/调试工具 UI（tools-programmer）。
模型层级：Sonnet（默认值）。
未分配 Gate ID。

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域特定（引用渲染/内存/引擎核心）
- [ ] `allowed-tools:` 列表包括 Read、Write、Edit、Bash、Glob、Grep
- [ ] 模型层级为 Sonnet（专家默认值）
- [ ] Agent 定义不声称对游戏机制或工具 UI 拥有权限

---

## 测试用例

### 用例 1：领域内请求 — 适当的输出
**输入：** "实现一个用于抛射物的自定义对象池以避免每帧分配。"
**预期行为**：
- 生成引擎级对象池实现，带 acquire/release 接口
- 池类型化为抛射物对象类型，使用预分配的固定大小存储
- 提供线程安全说明（或清楚标记为仅单线程并附理由）
- 按照编码标准在公共 API 上包含文档注释
- 输出与项目配置的引擎和语言兼容

### 用例 2：领域外请求 — 正确重定向
**输入：** "添加一个带音量滑块和'返回主菜单'按钮的暂停菜单屏幕。"
**预期行为**：
- 不生成 UI 屏幕代码
- 明确声明菜单屏幕属于 `ui-programmer`
- 将请求重定向给 `ui-programmer`
- 可能注明它可以提供引擎级音频音量 API 端点供 ui-programmer 调用

### 用例 3：内存泄漏诊断
**输入：** "每次关卡加载内存使用增长约 50MB 且从不释放。我们怀疑是资源加载系统。"
**预期行为**：
- 生成系统诊断方法：引用计数审计、资源句柄生命周期检查、缓存失效审查
- 识别可能原因（孤立资源句柄、循环引用、永不逐出的缓存）
- 为识别的泄漏模式生成具体修复
- 提供测试验证修复（加载前内存基线，卸载后测量，确认返回基线）

### 用例 4：跨域协调 — 共享系统优化
**输入：** "我需要优化物理 broadphase，但游戏系统与物理查询 API 紧密耦合。"
**预期行为**：
- 不单方面更改物理查询 API 接口（会破坏 gameplay-programmer 的代码）
- 与 `lead-programmer` 协调安全规划变更
- 提出迁移路径：新优化 API 与旧 API 并存，带废弃期
- 在继续之前记录协调需求

### 用例 5：上下文传递 — 检查引擎版本参考
**输入：** 上下文中提供了引擎版本参考（Godot 4.6）。请求："为项目设置默认物理引擎。"
**预期行为**：
- 读取引擎版本参考并注意 Godot 4.6 变更：Jolt 物理现在是默认值
- 生成考虑 Jolt 作为默认变更的配置指南（4.6 迁移说明）
- 标记 GodotPhysics 与 Jolt 之间可能影响现有代码的任何 API 差异
- 不建议已废弃或 4.6 之前的物理设置步骤，除非注明它们适用于旧版本

## 协议合规

- [ ] 保持在声明领域内（渲染、物理、内存、资源加载、核心框架）
- [ ] 将 UI/菜单请求重定向给 ui-programmer
- [ ] 返回结构化发现（实现代码、诊断步骤、迁移计划）
- [ ] 在更改共享 API 接口之前与 lead-programmer 协调
- [ ] 在建议引擎特定 API 之前检查引擎版本参考
- [ ] 为修复提供测试证据（内存前后、性能测量）

## 覆盖说明
- 对象池（用例 1）必须在 `tests/unit/engine/` 中包含单元测试
- 内存泄漏诊断（用例 3）应在 `production/qa/evidence/` 中生成证据工件
- 引擎版本检查（用例 5）确认 Agent 将 VERSION.md 视为权威，而非 LLM 训练数据
