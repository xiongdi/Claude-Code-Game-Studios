# Agent 测试规格：network-programmer

## Agent 摘要
领域：多人网络、状态复制、延迟补偿、匹配协议设计和网络消息模式。
不负责：游戏逻辑（仅其网络部分）、服务器基础设施和部署（devops-engineer）。
模型层级：Sonnet（默认值）。
未分配 Gate ID。

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且领域特定（引用多人/复制/网络）
- [ ] `allowed-tools:` 列表包括 Read、Write、Edit、Bash、Glob、Grep
- [ ] 模型层级为 Sonnet（专家默认值）
- [ ] Agent 定义不声称对游戏逻辑或服务器部署基础设施拥有权限

---

## 测试用例

### 用例 1：领域内请求 — 适当的输出
**输入：** "为 4 人合作游戏中的玩家位置设计状态复制。"
**预期行为：**
- 生成一个同步策略文档，涵盖：
  - 复制频率（例如 20Hz 带增量压缩）
  - 优先级层（例如自身玩家高优先级，其他玩家中优先级）
  - 远程玩家的插值方法（例如带 100ms 缓冲的线性插值）
  - 每玩家每秒带宽估计
- 不实现玩家移动逻辑本身（推迟给 gameplay-programmer）
- 提出死推测或预测策略以减少可见延迟

### 用例 2：领域外请求 — 正确重定向
**输入：** "将我们的游戏服务器部署到 AWS EC2 并设置自动扩展。"
**预期行为：**
- 不生成服务器部署配置、Terraform 或 AWS 设置脚本
- 明确声明服务器基础设施属于 `devops-engineer`
- 将请求重定向给 `devops-engineer`
- 可能注明一旦基础设施设置完成，可以提供服务器需要实现的网络协议规格

### 用例 3：状态分歧 — 回滚/协调
**输入：** "在高延迟下，客户端在物理对象上与权威服务器状态分歧。"
**预期行为：**
- 提出回滚和协调方法（客户端预测 + 权威服务器校正）
- 指定状态快照格式、协调触发阈值（例如 >5 单位位置误差）和校正插值速度
- 注明确定性回滚的输入缓冲模式
- 不更改物理模拟本身——记录 engine-programmer 的接口契约

### 用例 4：反作弊冲突
**输入：** "我们希望客户端权威位置以实现平滑移动，但反作弊需要服务器验证。"
**预期行为：**
- 呈现直接冲突：客户端权威快速但可利用；服务器权威安全但需要延迟补偿
- 与 `security-engineer` 协调达成验证边界
- 提出妥协（服务器在容差带内验证位置，标记异常值）而非单方面决定
- 记录权衡，如果 security-engineer 和 network-programmer 无法达成一致，将最终决策升级给 `technical-director`

### 用例 5：上下文传递 — 延迟预算
**输入：** 上下文中提供了技术偏好：目标延迟 95% 玩家 80ms RTT。请求："为格斗游戏设计输入复制方案。"
**预期行为：**
- 在设计中明确引用 80ms RTT 预算
- 选择针对该预算校准的复制方法（例如，在此延迟下格斗游戏首选回滚网络代码）
- 指定从 80ms 预算计算的输入延迟帧（例如，60fps 下 2 帧 = 33ms 缓冲）
- 标记回滚网络代码需要 gameplay-programmer 实现确定性模拟

## 协议合规

- [ ] 保持在声明领域内（复制、延迟补偿、协议设计、匹配）
- [ ] 将服务器部署重定向给 devops-engineer
- [ ] 返回结构化发现（同步策略、协议规格、带宽估计）
- [ ] 不实现游戏逻辑——仅指定其网络契约
- [ ] 在反作弊边界与 security-engineer 协调
- [ ] 根据提供的上下文中的明确延迟目标设计

---

## 覆盖说明
- 复制策略（用例 1）应包括 technical-director 可审查的带宽计算
- 回滚/协调（用例 3）必须清楚记录 engine-programmer 接口契约
- 反作弊冲突（用例 4）确认 Agent 升级而非单方面决定安全权衡
