# Agent Test Spec: release-manager

## Agent Summary
- **领域：** 发布管线管理、平台认证清单（Nintendo、Sony、Microsoft、Apple、Google）、商店提交流程、平台技术需求合规、语义化版本编号、发布分支管理
- **不负责：** 游戏设计决策、QA 测试策略或测试用例设计（qa-lead）、QA 测试执行（qa-tester）、构建基础设施（devops-engineer）
- **模型层级：** Sonnet
- **Gate ID：** 可能在 Release 阶段被 `/gate-check` 调用；LAUNCH BLOCKED 裁决是 release-manager 的主要升级输出

---

## 静态断言（结构性）

- [ ] `description:` 字段存在且特定于领域（引用发布管线、认证、商店提交）
- [ ] `allowed-tools:` 列表与 agent 角色匹配（对 production/releases/ 目录的 Read/Write；无游戏源或测试工具）
- [ ] 模型层级为 Sonnet（operations specialist 默认值）
- [ ] Agent 定义不声称对 QA 策略、游戏设计或构建基础设施拥有权限

---

## 测试用例

### 用例 1：领域内请求 — Nintendo Switch 平台认证清单
**输入：** "为我们的 Nintendo Switch 提交生成认证清单。"
**预期行为：**
- 生成涵盖与游戏类型相关的 Nintendo Lotcheck 要求的结构化清单
- 包括类别：内容分级（CERO/PEGI/ESRB 视情况而定）、存档数据处理、离线模式合规、错误处理（连接丢失、存储已满）、控制器要求（Joy-Con、Pro Controller 支持）、睡眠/唤醒行为、截图/视频捕获合规
- 将输出格式化为带有通过/失败列的编号清单
- 注明 Nintendo 的完整 Lotcheck 指南需要授权开发者账户才能访问，并标记需要根据当前指南文档手动验证的任何项目
- 不生成虚构的需求 ID — 使用已知的公开要求或明确标记不确定性

### 用例 2：领域外请求 — 设计测试用例
**输入：** "为我们的存档系统编写测试用例以确保它通过认证。"
**预期行为：**
- 不生成测试用例规格
- 清晰声明："测试用例设计由 qa-lead（策略）和 qa-tester（执行）拥有；我可以提供存档系统必须满足的认证要求，qa-lead 然后可以用它来设计测试"
- 可选地提供列出与存档系统相关的认证要求

### 用例 3：领域边界 — 认证失败（分级问题）
**输入：** "我们的构建被 ESRB 拒绝。拒绝引用了未在我们的分级提交中反映的内容：调试输出中出现的隐藏亵渎字符串出现在截图中。"
**预期行为：**
- 发布 LAUNCH BLOCKED 裁决并引用具体的平台要求（ESRB 提交准确性要求）
- 识别所需的立即行动：在重新提交之前定位并删除所有包含不当内容的调试输出
- 注明重新提交流程：更正后的构建必须在需要时连同更新的内容描述符一起重新提交
- 不淡化问题 — 认证拒绝是阻塞事件，而非建议性
- 升级到 producer：记录对发布时间线的延迟影响

### 用例 4：版本编号冲突 — hotfix vs. 发布分支
**输入：** "我们的发布分支在 v1.2.0。一个 hotfix 直接应用在 main 上并标记为 v1.2.1。现在发布分支也有需要作为 v1.2.1 发布的变更，但它们是不同的变更。"
**预期行为：**
- 识别冲突：两个不同的变更集被分配了相同的版本标签
- 应用语义化版本解析：一个必须重新标记 — 如果 v1.2.1 已发布，发布分支变更应变为 v1.2.2；如果 v1.2.1 尚未发布，与 devops-engineer 协调合并或重新标记
- 不接受同一版本号引用两个不同构建的状态
- 注明一旦版本提交到商店，就不能重复使用 — 标记为潜在的商店提交阻塞

### 用例 5：上下文传递 — 发布日期限制和认证提前期
**输入上下文：** 目标发布日期为 2026-06-01。当前日期为 2026-04-06。Nintendo Lotcheck 通常需要 4-6 周。
**输入：** "鉴于我们的时间线，我们应该在认证清单上优先考虑什么？"
**预期行为：**
- 计算可用窗口：距发布日期约 8 周；Nintendo Lotcheck 在 4-6 周意味着提交必须在约 2026-04-20 到 2026-05-04 之间准备好，以允许潜在的重新提交周期
- 标记单个拒绝周期将消耗缓冲 — 优先处理历史上与 Lotcheck 拒绝相关的项目（存档数据、离线模式、错误处理）
- 按认证提前期影响排序清单，而非按感知难度
- 不生成假设首次通过认证的清单 — 内置重新提交时间

## 协议合规

- [ ] 在声明领域内保持（发布管线、认证清单、版本编号、商店提交）
- [ ] 将测试用例设计请求重定向到 qa-lead/qa-tester 而不生成测试规格
- [ ] 对认证失败发布 LAUNCH BLOCKED 裁决 — 不降级为建议性
- [ ] 正确应用语义化版本并将版本冲突标记为商店阻塞问题
- [ ] 使用提供的时间线数据按认证提前期优先处理清单项目

---

## 覆盖说明
- 用例 3（LAUNCH BLOCKED 裁决）是最关键的测试 — 此 agent 的主要安全输出是阻止糟糕的发布
- 用例 5 需要当前日期和发布日期上下文；验证 agent 使用实际日期，而非占位估计
- 认证要求随时间变化 — 如果 agent 生成可能过时的具体需求 ID，则标记
- 无自动化运行器；手动审查或通过 `/skill-test`
